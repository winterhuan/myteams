# myteams v1.2 可理解性诊断报告

> 诊断视角：非技术用户「能不能看懂、能不能驾驭」
> 诊断对象：`docs/myteams-方案.md` v1.2
> 日期：2026-07-06
> 诊断人：ux-reviewer

---

## 0. 总体判断（先说结论）

**v1.2 方案设计精巧、能力完整，但对非技术用户的概念负担过重。** 核心问题不是「功能不够」，而是「用户要理解的概念太多、层级太深、命名太洋」。

一句话概括：**这是一份工程师写给工程师的方案，不是一份用户能「一眼看懂」的方案。**

方案里同时存在约 20 个核心概念，抽象链路最深处达 6 层（Team→Mission→Phase→Engagement→Ledger→WorkCard），并且大量使用 Charter/Briefing/Engagement/Ledger/Custody/Closeout 这类英文术语。用户日常只需要理解 4-5 个概念就能驾驭，其余应当作为内部实现隐藏掉。

下面逐项诊断并给出可操作建议。

---

## 1. 概念负担清单

下表列出方案中出现的全部核心概念，逐个评估认知负担，并标注「用户必须懂」还是「内部可隐藏」。

| 概念 | 方案中的定义 | 认知负担 | 用户必须懂吗 | 建议 |
|------|--------------|----------|--------------|------|
| **Team**（团队/编队） | 专业编队，长期存在，跨多个 Mission | 低 | ✅ 必须 | 保留，中文化为「团队」 |
| **Member**（成员） | 队内角色（Agent 或人） | 低 | ✅ 必须 | 保留，中文化为「成员」或「队员」 |
| **Mission**（任务/作品） | 一件作品或项目 | 低 | ✅ 必须 | 保留，按场景叫「作品/项目」更直观 |
| **Charter**（队宪） | 队宪：使命、自治边界、升级条件 | 高 | ⚠️ 半懂即可 | 重命名为「队规」，用户只需知道「队规规定了哪些事不用问你、哪些事必须问你」 |
| **Briefing**（团队记忆） | principles/patterns/scars | 中 | ✅ 必须 | 重命名为「团队笔记本」或「团队经验」，用户只需知道「团队会自己记笔记、越来越聪明」 |
| **Phase**（阶段） | brainstorm/scheme/delivery | 中 | ✅ 必须 | 保留，中文化为「阶段」，且固定为「头脑风暴→定方案→实施」三段，不让用户自定义阶段名 |
| **Engagement**（活跃工作） | 在某 Mission·Phase 上的一次活跃工作 | 高 | ❌ 可隐藏 | **合并/隐藏**：用户不需要这个概念，它是内部执行单元。用户只看到「团队在某个阶段干活」 |
| **Ledger**（时间线） | append-only 队内时间线 | 中 | ⚠️ 半懂即可 | 重命名为「队内动态」或「工作日志」，用户只需知道「这里能看到团队说了什么、做了什么」 |
| **Closeout**（收尾） | Phase/Mission 收尾的结构化沉淀 | 高 | ❌ 可隐藏 | **合并/隐藏**：合并进 Briefing 更新流程，用户只看到「项目结束后团队自动记了笔记」 |
| **Board**（看板） | 某 Mission 的工作看板 | 低 | ✅ 必须 | 保留，中文化为「看板」 |
| **Column**（列） | 看板列 | 低 | ✅ 必须 | 保留，中文化为「列」，且用模板预置不让用户从零定义 |
| **WorkCard**（工作卡） | 可指派、可追踪的工作单元 | 低 | ✅ 必须 | 保留，中文化为「卡片」或「任务卡」 |
| **Thread**（轻协作） | 探索、创意碰撞、对等讨论 | 中 | ⚠️ 半懂即可 | 用户不需要知道「Thread vs WorkflowRun」这个二分法，改为「这支队默认怎么干活」由模板决定 |
| **WorkflowRun**（流程执行） | 步骤清晰、需审批、可重试 | 中 | ⚠️ 半懂即可 | 同上，合并为「工作方式」，不让用户显式选择 |
| **EngineAdapter**（引擎适配） | 统一调度接口，对接多 Harness | 高 | ❌ 可隐藏 | **完全隐藏**：用户不需要知道引擎适配层 |
| **Harness**（执行底座） | Pi/Codex/Claude/acpx | 高 | ❌ 可隐藏 | **完全隐藏**：用户最多知道「团队用什么 AI 干活」，不需要知道 Harness 概念 |
| **Custody**（责任/球权） | 当前责任方 | 中 | ❌ 可隐藏 | **合并**：与 WorkCard 的 assignee 合并，用户只看到「这张卡现在谁负责」 |
| **Autonomy L0–L3**（自治等级） | 仅建议/可逆/可回滚/不可逆 | 中 | ⚠️ 半懂即可 | 用户只需知道「哪些事团队自己能定、哪些事必须问你」，不需要记 L0/L1/L2/L3 四个等级 |
| **Escalation**（升级） | 待人拍板 | 中 | ✅ 必须 | 重命名为「待你拍板」，做成一个队列，用户一眼看到 |
| **Hub**（现场） | 人看现场、做 L3 决策 | 低 | ✅ 必须 | 保留，中文化为「控制台」或「工作台」 |

**统计**：
- 必须懂：9 个（Team/Member/Mission/Phase/Board/Column/WorkCard/Briefing/Escalation/Hub）
- 半懂即可：5 个（Charter/Ledger/Thread/WorkflowRun/Autonomy）
- 可隐藏：6 个（Engagement/Closeout/EngineAdapter/Harness/Custody + 部分内部细节）

**结论**：用户必须懂的概念有 9-10 个，仍然偏多。目标是压到 4-5 个「日常核心」+ 2-3 个「偶尔碰到」。

## 2. 抽象层级诊断

### 2.1 层级过深的地方

方案中存在多条过深的抽象链路：

**链路 A：Team → Mission → Phase → Engagement → Ledger → WorkCard（6 层）**

这是最重的一条。用户想看「我的团队在干什么」，脑子里要走完 6 层才能定位到一张卡片。实际日常使用中，用户的心智模型应该是：

```
我养了哪支团队 → 这支队在做什么作品 → 这件作品现在进展如何（看板）
```

只有 3 层。Phase 应该是看板的「视图筛选器」而不是独立概念；Engagement/Ledger 应该是卡片背后的「详情页」而不是独立层级。

**链路 B：Engagement 执行 → Closeout → Briefing 更新 → Charter 微调 → 下次带上（5 步进化循环）**

这条「进化循环」逻辑正确，但作为用户理解路径太长。用户的心智模型应该是：

```
团队做完一个作品 → 自动记笔记 → 下次更聪明
```

只有 3 步。Closeout 应该合并进 Briefing 更新，Charter 微调应该是「团队自动优化队规」而非用户显式操作。

**链路 C：Team → Charter → Autonomy L0–L3 → Escalation（4 层决策链）**

用户想理解「哪些事需要我拍板」，要走完 4 层。实际心智模型应该是：

```
队规里写了哪些事必须问我 → 这些事会进「待你拍板」队列
```

只有 2 层。L0–L3 等级是内部实现，用户不需要记。

### 2.2 扁平化建议

| 现有层级 | 建议扁平化后 |
|----------|--------------|
| Team → Mission → Phase → Engagement → Ledger → WorkCard | **Team → 作品 → 看板卡片**（Phase 变成看板筛选器，Engagement/Ledger 变成卡片详情） |
| Engagement → Closeout → Briefing → Charter 微调 | **作品完成 → 团队自动记笔记**（Closeout 合并，Charter 微调自动） |
| Team → Charter → Autonomy L0–L3 → Escalation | **队规 → 待你拍板队列**（L0–L3 隐藏） |
| Thread / WorkflowRun / Hybrid 三选一 | **团队模板预置工作方式**（用户不显式选模式） |

## 3. 最小可理解概念集

用户日常使用时，脑子里应该只有以下 **5 个核心概念**：

### 3.1 日常核心 5 件套

| # | 概念 | 用户脑中的理解 | 对应方案对象 |
|---|------|----------------|--------------|
| 1 | **团队**（Team） | 「我养了几支专业队伍，比如短剧队、小说队、开发队」 | Team |
| 2 | **作品**（Mission） | 「这支队现在在做哪件活，比如第 1 季短剧、第 2 本小说」 | Mission |
| 3 | **看板**（Board + WorkCard） | 「这件活的进展，分成几张卡，谁在干、卡在哪」 | Board + Column + WorkCard |
| 4 | **团队笔记本**（Briefing） | 「这支队记住了什么经验，会越来越聪明」 | Briefing |
| 5 | **待你拍板**（Escalation） | 「有哪些事团队拿不准，在等你决定」 | Escalation 队列 |

### 3.2 偶尔碰到的 3 件套

| # | 概念 | 用户脑中的理解 | 何时碰到 |
|---|------|----------------|----------|
| 6 | **队规**（Charter） | 「这支队哪些事能自己定、哪些事必须问我」 | 建队时看一眼，之后偶尔调整 |
| 7 | **队内动态**（Ledger） | 「团队内部说了什么、做了什么」 | 想追溯细节时点开看 |
| 8 | **阶段**（Phase） | 「这件活在头脑风暴、定方案、实施哪一段」 | 看看板上方的阶段条 |

### 3.3 完全隐藏的内部概念

以下概念用户**永远不需要看到**，作为内部实现：

- Engagement（活跃工作）→ 内部执行调度单元
- Closeout（收尾）→ 合并进笔记本更新流程
- Thread / WorkflowRun → 模板预置，用户不选
- EngineAdapter / Harness → 执行层细节
- Custody（球权）→ 合并进卡片的 assignee
- Autonomy L0–L3 → 内部决策等级，对用户只暴露「待你拍板」队列

## 4. 命名优化建议

现有方案大量使用英文术语，对中文用户不直观。建议全面中文化，并用「生活化比喻」替代「学术/工程术语」。

| 原命名 | 建议中文名 | 理由 |
|--------|------------|------|
| Team | **团队** | 直白，不需要「编队」这种军事化用语 |
| Member | **成员** / **队员** | 直白 |
| Mission | **作品**（创作类）/ **项目**（开发类） | 按场景叫更直观，「Mission」太军事化 |
| Charter | **队规** | 「队宪」太正式像法律文件，「队规」像班级公约，亲切易懂 |
| Briefing | **团队笔记本** | 「Briefing」是军事情报术语；「笔记本」让用户秒懂「团队会记笔记变聪明」 |
| Phase | **阶段** | 保留，但固定为「头脑风暴→定方案→实施」 |
| Engagement | （隐藏，不命名） | 用户不需要这个概念 |
| Ledger | **队内动态** | 「Ledger」是会计账本术语；「动态」像朋友圈，用户秒懂 |
| Closeout | （隐藏，合并进笔记本） | 用户只看到「项目结束，团队记了笔记」 |
| Board | **看板** | 保留 |
| Column | **列** | 保留，但用模板预置 |
| WorkCard | **卡片** / **任务卡** | 「WorkCard」直译太硬，「卡片」更轻 |
| Thread | （隐藏，合并进「工作方式」） | 用户不选模式 |
| WorkflowRun | （隐藏，合并进「工作方式」） | 用户不选模式 |
| EngineAdapter | （隐藏） | 内部实现 |
| Harness | （隐藏） | 内部实现，最多说「AI 引擎」 |
| Custody | （隐藏，合并进 assignee） | 用户只看「卡片谁负责」 |
| Autonomy L0–L3 | （隐藏，只暴露「待你拍板」） | 用户不需要记等级 |
| Escalation | **待你拍板** | 「Escalation」是工程术语；「待你拍板」直接告诉用户「该你了」 |
| Hub | **工作台** | 「Hub」是技术术语；「工作台」像木工台、画板，亲切 |

## 5. 可见性设计建议

### 5.1 现有 Hub 三视图的问题

方案现有三视图：**看板 / 时间线（Ledger）/ 阶段**。

问题：
1. **缺少「多团队总览」**：用户养了 3 支队，但 Hub 默认 landing 是「选 Team → 看 Mission 看板」。用户想一眼看见「3 支队都在干什么」没有入口。方案 Phase 3 才做「跨 Team 委托人仪表盘」，太晚。
2. **三视图并列但权重不均**：方案说「委托人默认看板」，但时间线和阶段视图的切换关系不清晰。用户会困惑「我该看哪个」。
3. **「阶段」视图太抽象**：阶段是个流程概念，单独做成视图不如做成看板上方的「进度条」。

### 5.2 建议：四层视图 + 顶部团队总览

```
工作台
  ├── 【团队总览】首页：一眼看见所有团队在干什么（新增，最重要）
  ├── 【看板】某团队·某作品的看板（默认详情页）
  ├── 【队内动态】看板背后的对话与决策日志（原时间线）
  └── 【待你拍板】跨所有团队的待决策队列（独立入口，始终可见）
```

#### 5.2.1 团队总览页（新增，作为首页）

用户打开工作台，第一眼看到的是**所有团队的卡片墙**：

```
┌─────────────────────────────────────────────────────────┐
│  我的团队                                          [+建队]│
├──────────────────┬──────────────────┬────────────────────┤
│ 🎬 短剧队         │ 📖 小说队         │ 💻 应用开发队       │
│ 第1季·第3集       │ 第2本·第8章       │ 待办应用 MVP        │
│ ●实施中 5/8卡     │ ●写作中 3/12章    │ ●定方案 待你拍板1项  │
│ 上次活动 2小时前  │ 上次活动 10分钟前 │ 上次活动 刚刚        │
│ [进入看板]        │ [进入看板]        │ [进入看板]          │
└──────────────────┴──────────────────┴────────────────────┘
```

每张团队卡片回答 4 个问题：
- 哪支队
- 在做什么作品
- 进展到哪、几张卡
- 有没有卡住/待拍板

**这是用户最需要的「一眼看见」**，方案里缺失。

#### 5.2.2 看板视图（默认详情页）

点进某团队后，默认看该作品的看板。看板上方加一条**阶段进度条**，替代独立的「阶段视图」：

```
第1季·第3集    [头脑风暴 ✓]——[定方案 ✓]——[●实施中] 
┌─────────┬─────────┬─────────┬─────────┐
│ 待写     │ 写作中   │ 待审    │ 完成     │
│  编号1   │  编号3   │  编号5  │  编号7  │
│  编号2   │ @编剧    │ @导演   │  编号8  │
│         │  编号4   │ ⚠阻塞   │         │
└─────────┴─────────┴─────────┴─────────┘
```

#### 5.2.3 待你拍板队列（始终可见）

不管在哪个视图，顶部常驻一个**「待你拍板(N)」**入口，点开是跨所有团队的待决策列表。这是用户作为「委托人」最重要的入口，不能埋在某个团队内部。

### 5.3 阶段视图的处理

**建议砍掉独立的「阶段视图」**，把它降级为看板上方的进度条。用户不需要单独切换到「阶段视图」看自己在哪一段——进度条一眼就看见了。三视图变两视图（看板 + 队内动态），认知负担更低。

## 6. 进化机制简化建议

### 6.1 现有进化机制的理解负担

方案现有进化循环：

```
Engagement 执行（带 Briefing 上下文）
  → Closeout（队自定义：什么管用/什么翻车）
  → Briefing 更新（principles/patterns/scars）
  → Charter/工作方式微调
  → 下次自动带上
```

用户要理解这个循环，需要懂 Engagement、Closeout、Briefing、Charter 四个概念，还要理解 principles/patterns/scars 三种记忆类型。太重。

### 6.2 简化建议：把进化变成「团队自动记笔记」

**用户侧心智模型（只 3 步）**：

```
团队做完一件作品 → 团队自动在笔记本上记笔记 → 下次做新作品时更聪明
```

#### 6.2.1 Closeout 合并进「自动记笔记」

不要让用户理解「Closeout」这个独立环节。作品完成时，系统自动触发笔记更新，用户只看到一条动态：

> 「📖 小说队完成了第2本，记了3条经验：①伏笔要提前2章埋 ②文风统一用POV-A ③第5章节奏拖沓，下次注意」

用户不需要知道这叫 Closeout，只需要看到「团队记笔记了」。

#### 6.2.2 Briefing 的三种记忆类型对用户隐藏

principles/patterns/scars 是内部结构，用户不需要区分。用户看到的「团队笔记本」就是一份**可读的笔记文档**，按时间倒序排列，每条笔记标注「来自哪件作品」。

```
📚 团队笔记本

[第2本·2026-06] 
- 伏笔要提前2章埋（经验）
- 第5章节奏拖沓，下次注意（教训）

[第1本·2026-03]
- POV-A 文风适合主线推进（经验）
- 人物出场不超过3个新角色/章（经验）
```

#### 6.2.3 Charter 微调自动化

方案里「Charter/工作方式微调」需要用户理解「队可以在自治边界内微调」。建议改为：

- **队规的微调由团队自动发起**，用户只在「待你拍板」里看到「团队建议改这条队规，同意吗？」
- 用户不需要主动改队规，团队会自己提建议
- L3 级别的队规变更才找用户批，其余团队自己改

这样用户对「进化」的理解就是：**团队会自己变聪明，偶尔问我同不同意改规则**。

### 6.3 用户能看到「团队变聪明」的证据

在团队总览页，每张团队卡片下方加一行：

> 「累计经验 12 条 · 教训 5 条 · 上次记笔记 3 天前」

让用户直观感到「这支队在积累」，而不是一个黑盒。

## 7. 自定义工作方式简化建议

### 7.1 现有自定义的理解负担

方案现有自定义机制：
- Charter（队宪）自治边界自定
- 三阶段内容、角色、产物自定
- Thread / WorkflowRun / Hybrid 三种协作模式选一种
- 看板列自定
- Phase 门禁自定

这对用户是「太多自由反而迷茫」。用户想建一支短剧队，面对的是：
- 队宪怎么写？
- 三阶段每阶段产物是什么？
- 选 Thread 还是 Hybrid？
- 看板列设几列、叫什么？
- 门禁怎么配？

这是「从零搭系统」的负担，不是「养一支队」的体验。

### 7.2 建议：模板 + 微调，不让用户从零定义

#### 7.2.1 三套现成模板（开箱即用）

方案里已经写了三支队的工作方式（§5.1-5.3），直接把它们做成**官方模板**：

```
建队时选模板：
  🎬 短剧创作队  —— 选题/编剧/导演/剪辑，看板列已配好
  📖 小说创作队  —— 主笔/世界观/连贯审/文风审，看板列已配好
  💻 应用开发队  —— 架构/构建/审查，看板列已配好
  ⚙️ 自定义      —— 高级用户从零配（默认折叠）
```

选模板后，**队规、阶段、成员、看板列、协作模式全部预置**，用户一键建队。

#### 7.2.2 微调而非自定义

建队后，用户能微调的只有 3 件事：

1. **成员**：加人/减人/改角色人格（比如换个编剧风格）
2. **看板列**：加列/改列名/删列（比如短剧队加一列「素材准备」）
3. **队规的「必须问我」清单**：加减哪些事必须人批

**不暴露给用户的**：
- 协作模式选择（模板预置，短剧/小说默认 Thread，开发默认 Hybrid）
- Phase 门禁配置（模板预置，开发队的「定方案」必须人批，短剧/小说的「定方案」人批方向即可）
- 阶段产物清单（模板预置，用户只在看板卡片里看到产物）

#### 7.2.3 模板的内部结构（用户不看）

模板内部仍然是方案定义的结构（Charter + Phase + 成员 + 看板列 + 协作模式），但这些对用户隐藏。用户看到的是：

```
你选了「短剧创作队」模板
  → 成员：总策划、编剧、导演、剪辑（可改）
  → 看板：选题池→大纲定稿→拍摄制作→待审→完成（可改列）
  → 队规：发布成品必须问你，其余团队自己定（可调）
  → [一键建队]
```

#### 7.2.4 「自定义」入口默认折叠

只有高级用户想「从零搭一支特殊队伍」时，才展开「自定义」入口。99% 的用户用模板 + 微调就够了。

### 7.3 模板可演进

模板本身也会随平台进化——当平台发现「很多短剧队都自己加了一列『素材准备』」，可以把这一列纳入官方模板。这是后话，但保证了模板不会僵化。

## 8. 额外发现：方案中的几个可理解性细节问题

### 8.1 「两层结构」对用户无意义

方案 §3.1 的「两层结构」（平台层 / Team 层）是架构视角，用户不需要理解。用户只看到「我的团队」。建议在面向用户的产品文档里完全不提「两层结构」。

### 8.2 「Harness 中立」对用户无意义

方案反复强调「Harness 中立」「EngineAdapter」，这是技术立场，不是用户价值。用户只关心「这支队用什么 AI 干活，能不能换」。建议对外只说「团队支持多种 AI 引擎，可切换」，不提 Harness/Adapter 概念。

### 8.3 YAML 配置对用户不友好

方案 §3.4 的配置示例是 YAML。非技术用户不写 YAML。建议：
- 建队用「表单 + 模板选择」
- 队规微调用「开关 + 文本框」
- 看板列用「拖拽增删列」
- YAML 只作为「高级用户/版本化」的后端存储格式，不暴露给用户

### 8.4 「委托人」这个词偏正式

「委托人」像法律用语。建议产品里叫**「队主」或「我」**——用户就是这些团队的主人，不需要「委托」这个动作来定义身份。

## 9. 诊断总结：三条最关键的简化建议

如果只能做三件事来提升可理解性，优先做这三件：

### 建议 1：概念瘦身——从 20 个压到 5 个日常核心

用户日常只理解 **团队 / 作品 / 看板 / 团队笔记本 / 待你拍板** 这 5 个概念。Engagement、Closeout、Thread/WorkflowRun、EngineAdapter、Harness、Custody、Autonomy L0–L3 全部作为内部实现隐藏。Charter 降级为「队规」且用户半懂即可，Ledger 降级为「队内动态」且只在做细节追溯时点开。

### 建议 2：命名中文化 + 生活化比喻

全面替换英文术语：Briefing→团队笔记本、Charter→队规、Ledger→队内动态、Escalation→待你拍板、Hub→工作台。命名原则是「用生活化比喻替代学术/工程术语」，让用户看名字就懂意思。

### 建议 3：模板 + 微调替代从零自定义

提供短剧/小说/应用开发三套官方模板，用户建队时一键选择，队规/阶段/成员/看板列/协作模式全部预置。用户只能微调「成员、看板列、必须问我的事」这三项，其余隐藏。99% 用户用模板，1% 高级用户才展开「自定义」。
